# Browser shell and renderer

`web/` is the page that runs the built game (`dist/oot.js`, produced by `npm run port`). `npm run dev -- --port <p> --strictPort` serves it and serves `dist/oot.js`, `dist/oot.wasm` and `dist/game.pack` at the site root; `npm run build` writes `dist/web/` and copies the two game files beside the page, not the pack: the pack (the cartridge image) stays in `dist/` and the dev and preview servers hand it to loopback clients only (`web/game-files.ts`). Vite's own bundle is under `bundle/` (`build.assetsDir`).

- **ROM.** The page never asks for a ROM. `npm run port -- --rom <path>` (which checks the SHA-1) writes `dist/game.pack`: a 64-byte header (magic, image size, SHA-256 of the image) followed by the 32 MB cartridge image (`tools/assets/pack.ts`). The page fetches only that file (`web/cartridge.ts`), checks its length and hash before boot (a missing, truncated or altered pack gives a message that says to run `npm run port` again) and hands the image, a view into the downloaded buffer, to the runtime. `web/no-rom-file.test.ts` checks that the sources name no ROM file and use no file input or file-reading API. `npm run port` also still writes `dist/assets/` (every file of the file table as stored, plus `manifest.json`, see `docs/re/assets.md`): the page does not read it, but `npm run headless`, `npm run sweep` and the ROM-gated tests rebuild the image from it (`readCartridge`), and a ROM-gated test checks that the pack holds the same image byte for byte.
- **Wasm.** `web/wasm.ts` fetches `oot.wasm` once when the page starts, in parallel with the pack: `WebAssembly.compileStreaming` compiles the response while it downloads, and the game's `instantiateWasm` hook instantiates the compiled module. `oot.js` is preloaded at the same time.
- **Caching.** The dev and preview servers answer the pack, `oot.js` and `oot.wasm` with `ETag` (the pack's is the image hash from its header, the others are the SHA-256 of the file, remembered per size and modification time) and `Cache-Control: no-cache`: the browser keeps its copy and asks before every use, so a repeat visit costs a 304 and a rebuilt file is downloaded at the next load, never served stale. The wasm is ready (`compiled`) about 90 ms after page start on a repeat visit, against about 295 ms on the first.
- **Load time.** `web/timing.ts` marks the milestones in ms since navigation start (`header`: pack header received, `cartridge`: image verified, `compiled`, `instantiated`, `firstFrame`: first game frame shown); the debug overlay lists them and the total, and the page publishes them as `globalThis.ootTiming`. The status line says `Loading...`, and shows `Loading: X / Y MB` only after 0.5 s. `npx tsx tools/port/measure-load.ts [--port N] [--visits 3] [--assert]` (Windows only: it looks for Chrome at its default install path, `--chrome` overrides it, and stops processes with `taskkill`) starts the dev server, opens the page in headless Chrome (empty profile for the first visit, same profile after) and prints the milestones and request counts; `--assert` fails above 1500 ms (first visit) or 1000 ms (repeat).
  Measured with that script (Chrome 155 headless, dev server, this machine, `-O2` build, to the first game frame):
  | | before (1,512 assets) | after (one pack) |
  |---|---|---|
  | first visit | 5112 ms | 429-452 ms |
  | repeat visit | 2152-2295 ms | 221-230 ms |
  | requests (first / repeat) | 1548 / 1547 (2 for `oot.wasm`) | 37 / 36 (1 for the pack, 1 for `oot.wasm`; the rest are the page's Vite modules) |
  | data transferred (first / repeat) | 85.0 / 84.3 MB | 59.6 / 2.1 MB |
  | cartridge ready | 2819 / 1854 ms | 348-362 / 160-173 ms |
  Before, `oot.wasm` was downloaded twice and nothing was revalidated; the repeat visit still fetched every file.
- **Frame loop.** A `requestAnimationFrame` loop accumulates time and calls `oot_frame` once per video frame (`FramePacer` in `web/mode.ts`: 20 ms at 50 Hz, 1/60 s at 60 Hz, at most three catch-up frames). After the frames of an iteration it shows the colour image the video interface points at, read from the game's current `OSViContext` (`tools/gfx/vi.ts`); a blanked screen or an address nothing was drawn to shows black. A buffer the game is still drawing into is never shown, because the game only hands it to the video interface after its task.
- **Graphics tasks.** `Module.onGfxTask` runs the display-list interpreter of the module itself (`gfx_run` in `runtime/gfx/`, over the memory as the game left it), reads its result through `tools/gfx/c-dl.ts` and hands the batches to `Renderer`. The result is views into the module's memory, used before the next task runs. Colour images and the depth buffer have the size of the canvas as displayed, a whole multiple (1 to 4) of 320×240, so edges and bilinear texture filtering are not magnified from a small target; N switches to native 320×240 shown with hard pixels. The game never reads the colour images back through the page (the display lists are interpreted from guest memory), so resolution does not affect any readback. With Smooth on the task is kept instead of drawn and pictures between the last two game frames are drawn on each refresh (`docs/re/gaps.md`, "Interpolated rendering").
- **Colour and depth images.** Each colour image address the game draws into (`SETCIMG`) is a 320×240 texture, so double buffering works; there is one depth buffer, cleared by the fill rectangles the game draws while `SETCIMG` names the depth image address.
- **Debug overlay.** The Debug button on the page toggles it: frame and task counters, command, batch and triangle counts of the last task, unknown commands and interpreter problems, program and texture counts. C cycles face culling (normal, swapped, off), N toggles native resolution, and `#debug` on the URL opens the overlay.
- **Save states.** The key 5 saves to the current slot, 6 loads it and 7 selects the next slot (1-4, wrapping); a short notice shows the result, and stays longer when it is a refusal. The key only queues the action: the frame loop runs it between two frames. A save state records its mode and a state of the other mode is refused with a message (`Slot N was saved in 60 Hz mode; switch the mode and reload the page to load it`). A state is the portable format of `docs/runtime.md` ("Portable save states"), made by `rt_state_save` through `tools/runtime/snapshot.ts`, gzipped and kept with its format version, not with a build id: a state taken by one build loads into any later build that reads that version, so a rebuild does not lose it. Messages on the page: an empty slot, `Slot N uses state format X, this build reads Y` for another version, `Slot N was saved in the old format and cannot be loaded` for the build-locked memory dumps kept before the portable format, and `Slot N cannot be loaded: <reason>` when the runtime refuses the contents (an unknown function or call site, damaged data); a save refused because the game is booting or a thread is somewhere a state cannot hold shows `Save state failed: <reason>`. A refusal leaves the running game as it was and the stored state untouched. The save memory (the player's saved games) is not part of a restore, and the page's sound queue and renderer are not captured (about 0.1 s of sound is stale after a load).
- **Where saves live.** The dev and preview servers keep the SRAM save and the four states as files under `~/.zelda-oot-js/saves` (`OOT_SAVES_DIR` overrides), outside every checkout, through `/api/saves/sram` and `/api/saves/state/<1-4>` (`web/saves-endpoint.ts`; loopback clients only, only those names are ever mapped to a path). Every build reads the same SRAM save; each state carries its format version (`state-<n>.bin.format`). A state file with a `state-<n>.bin.build` beside it and no `.format` is from the old format: it is served as format 0, reported as above and never deleted or rewritten except by a new save into that slot. A page served without that endpoint falls back to IndexedDB (`zelda-oot-js`, `zelda-oot-js-states`), which is per origin and so not shared between ports; its records from before the portable format (they carry a build id) are read as the old format. When the endpoint answers, the page first copies whatever IndexedDB holds for this origin and the folder lacks (the SRAM save, each state slot, old-format ones included) to the folder, never overwriting, and leaves the IndexedDB copy alone.
- **60 Hz mode.** The "60 Hz" button next to Debug (not focusable by mouse, like Debug) stores the choice in `localStorage` (try/catch around every access; on by default; a stored choice wins). The game is booted at the stored rate, so a change applies at the next page load, which the page says next to the button; it never reloads. The overlay shows the mode and the measured game frames per second. A save state records its mode and a state of the other mode is refused with a message. See `docs/re/tv-type.md`.
- **Fast-forward.** Holding Tab (its focus change is suppressed) runs frames back to back for about 12 ms of each display frame and drops the game's sound instead of queueing it.

## GitHub Pages

`npm run pages:build` builds the site into git-ignored `dist-pages/` (`vite build --mode pages`: base `/zelda-oot-js/`; the page, `oot.js`, `oot.wasm` and `game.pack` copied from `dist/`, so `npm run port` must have run). `npm run pages:deploy` builds it, then force-pushes it as the single commit of the `gh-pages` branch of `origin` (`tools/pages/deploy.ts`) and enables Pages for that branch with `gh api`; if the API refuses, the script prints the setting to click (Settings > Pages > Deploy from a branch > `gh-pages`, `/ (root)`). The game files are published unencrypted: anyone with the URL can download the cartridge image. There is no saves endpoint on Pages, so saves use IndexedDB. The page and the game files are fetched from `import.meta.env.BASE_URL`; a compressed response to the pack is read without a preallocated length.

## Shaders

`web/shader.ts` builds one GLSL ES 3.00 fragment shader per `ShaderSpec`: the combiner inputs of both cycles, cycle type, filter mode, alpha compare, fog in shade alpha, and the blender selectors. Colours, tile sizes, masks and shifts are uniforms. Input selector numbering is the one `decodeCombine` already extracts; the meaning of each code, the blender selectors and the other-mode bit positions are from the RDP descriptions on n64brew.dev.

- Blender: `(p·a + m·b) / (a + b)`. A cycle that does not read the framebuffer is computed in the shader (this is how fog works). The last cycle, when it reads the framebuffer and the force-blend bit is set, outputs `p` with weight `a / (a + b)` in alpha and the GL blend unit does the rest; the framebuffer alpha is taken as 1.
- Coverage and alpha: other-mode bit 12 (coverage times alpha) discards a pixel whose alpha is below 32/255; bit 13 makes the blender's pixel alpha the coverage (1, or the pixel alpha with bit 12). Formulas and evidence in `docs/re/display-lists.md` section 7.
- Near plane (not clipped by the microcode, see `docs/re/display-lists.md` section 7): a vertex with `w > 0` and `z < -w` is moved to `z = -w` in the vertex shader, not clipped away (the status display's third heart is drawn there).
- Texture sampling: tile origin subtracted, shift, clamp, mirror and mask in the shader; 3-point bilinear when the filter bits are not zero, or four-texel bilinear (`smooth`) or nearest (`sharp`) by the graphics settings. Triangle draws can sample mip levels with anisotropic taps. Options, resolution rule, MSAA and measurements: `docs/re/gaps.md`, section "Texture filtering and sharpness". Keys: F filter, G multisampling, H mip levels.
- Depth: enabled by the geometry mode's z-buffer bit, compare and update by the other-mode bits, decal mode by a polygon offset.
- Fill rectangles in fill mode clear the rectangle (inclusive corners); in the other cycle types they draw through the combiner.

## Not verified against footage

The ROM was not run in a browser for this work, so these are open:
- front/back face orientation (`C` flips it);
- whether the second cycle's first texel input is the first cycle's second lookup;
- decal depth tolerance, coverage-based edge antialiasing (ignored), dithering (ignored), noise input (0.5).
